# LeadHub

Единая точка приёма заявок (лидов) малого бизнеса из разных источников
с надёжной доставкой и AI-обработкой.

Заявки приходят из разных каналов — сайт, Telegram, соцсети, объявления —
и теряются между ними. LeadHub сводит их в один поток: принимает, гарантированно
сохраняет, разносит по получателям и обогащает с помощью LLM.

## Что делает

```
                       ┌──────────────────────────────────────┐
источники              │            ЯДРО                      │        получатели
                       │                                      │
  сайт  ──┐            │   ┌──────────┐    ┌──────────────┐   │   ┌──> Google Sheets
          ├──вебхук──> │   │  очередь │ ─> │    воркер    │   │ ──┼──> Telegram
Telegram ─┘            │   │ (SQLite) │    │ ретраи, шаги │   │   └──> LLM: скоринг
  ...    ──┘           │   └──────────┘    └──────────────┘   │        + черновик ответа
                       └──────────────────────────────────────┘
```

Ключевая идея: приём и обработка разделены. Заявка сначала **гарантированно
попадает в локальную очередь**, и только потом воркер несёт её дальше. Если
Google Sheets, Telegram или LLM временно недоступны — лид не теряется,
он будет доставлен ретраем.

## Принципы

- **Лид не теряется никогда.** Приём отвечает `200 OK` только после записи в БД.
  Дальнейшие шаги — с ретраями и экспоненциальной задержкой.
- **Источники не зашиты в логику.** Канал — это данные (`source`), а не `if`.
  Новый источник = новый адаптер, ядро не меняется.
- **Предсказуемый AI.** Строгий системный промт, ответ по JSON-схеме,
  валидация и обработка случая «модель ответила мусором».
- **Секреты только в `.env`.** В репозитории лежит `.env.example` — шаблон.

## Запуск

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env      # затем заполнить значения
```

Приложение состоит из двух процессов — запускаются в разных терминалах:

```powershell
.\.venv\Scripts\python.exe -m app                    # приём заявок (HTTP)
.\.venv\Scripts\python.exe -m app.pipeline.worker    # обработка очереди
```

Они намеренно разделены: приём обязан отвечать за миллисекунды, а обработка
ходит в медленные внешние сервисы. Воркер можно перезапускать и обновлять,
не прерывая приём заявок, — накопленное в очереди обработается после старта.

Обслуживающая команда — доставить задачи лидам, у которых их нет
(например, после добавления нового шага в пайплайн):

```powershell
.\.venv\Scripts\python.exe -m app.pipeline.backfill
```

| Адрес | Что там |
|---|---|
| http://127.0.0.1:8000/ | тестовая форма — имитация формы на сайте клиента |
| http://127.0.0.1:8000/docs | интерактивная документация API |
| http://127.0.0.1:8000/healthz | состояние сервиса и разбивка лидов по статусам |

### Приём заявки

`POST /webhook/site` принимает и JSON, и обычную HTML-форму (`urlencoded`),
поэтому подключается и к самописному фронтенду, и к Tilda / WordPress.
Названия полей распознаются по распространённым вариантам
(`phone`, `tel`, `Телефон`, …).

```bash
curl -X POST http://127.0.0.1:8000/webhook/site \
     -H "Content-Type: application/json" \
     -d '{"name":"Иван","phone":"+79991112233","message":"Нужен сайт"}'
```

Коды ответов подобраны так, чтобы отправитель вёл себя правильно:

| Код | Значение | Должен ли отправитель повторить |
|---|---|---|
| `200` | заявка принята и лежит в очереди | нет |
| `400` / `415` | тело или Content-Type не разобрать | нет, повтор не поможет |
| `422` | данных не хватает (нет ни телефона, ни email) | нет |
| `401` | неверный `X-Webhook-Secret` | нет |
| `5xx` | сбой на нашей стороне | **да**, лид ещё не сохранён |

### Обработка сбоев

Каждый шаг обработки каждого лида — отдельная задача со своим счётчиком
попыток. Упавший шаг повторяется независимо от соседей, поэтому сбой Telegram
не приводит к повторной записи в таблицу.

- **Ретраи** — экспоненциальная задержка со случайным разбросом:
  2, 4, 8, 16, 32 сек (до потолка). Разброс не даёт накопившимся задачам
  ударить по восстановившемуся сервису одновременно.
- **Классы ошибок** — шаг сам различает временный сбой (повторяем) и
  постоянный, вроде `403 Forbidden` (сразу в разбор, не тратим попытки).
- **Dead letter** — задача, исчерпавшая попытки, не исчезает: остаётся в базе
  с историей и текстом ошибки, видна в `/healthz`.
- **Восстановление после падения** — задачи, зависшие в `processing`
  из-за убитого процесса, возвращаются в очередь при старте воркера.
- **Корректная остановка** — по `Ctrl+C` / `SIGTERM` воркер дорабатывает
  текущую задачу и выходит, не бросая лид на полпути.
